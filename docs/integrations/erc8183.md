# ERC-8183

**Status: working. Jobs are created, registered, funded and escrowed on BSC testnet from the product itself.**

Last verified: 2026-09-01, `@altananetwork/sdk@0.8.0`, BSC testnet (chain 97).

## What we intended

Commission a real job against an ERC-8183 seller from Pokter and follow it
through the escrow lifecycle — §34, and the "hire" end of the product loop.

## The bug we found, and fixed

> Reported upstream as
> [altananetwork/altana-sdk#84](https://github.com/altananetwork/altana-sdk/issues/84),
> with repro steps and an offer to PR the chain-97 entry.

`@altananetwork/sdk@0.8.0` **ships a stale OptimisticPolicy address for BSC
testnet.**

| | Policy address (chain 97) |
| --- | --- |
| `@altananetwork/sdk@0.8.0` | `0x4F4678D4439feC812Ac7674Bb3Efb4C8f5Fb78A6` |
| `@bnbagent/sdk@0.5.5` (reference) | `0xd6a4217588F6B1F5657a92A3e94E6422aD771cEA` |

`registerJob(jobId, policy)` against the stale address reverts `0xc94463e3` on
the EvaluatorRouter. `fund` then reverts `0x32d53d69`, because an unregistered
job cannot be funded. Mainnet agrees between the two SDKs; **only chain 97
diverges**, so `src/lib/erc8183/addresses.ts` overrides that one entry rather
than replacing the table.

### How it was found

The SDK batches all five buyer calls atomically, so the first failure was a
single opaque selector with no reason string. Attribution took three steps:

1. **Run the calls individually.** `createJob`, `setBudget` and `approve` all
   confirmed on-chain; `registerJob` and `fund` did not. That named the
   culprit but not the cause.
2. **Rule out the obvious.** Not funding (30 $U held, allowance exact, budget
   set on-chain); not the documented jobId race (deterministic across blocks);
   not a relay nonce artifact (reproduced with delays); not an outage — job
   **#863 COMPLETED at 0.1 $U with the same provider minutes earlier**.
3. **Diff against the reference implementation.** `@bnbagent/sdk`'s
   `networks/addresses.ts` carries a different policy address for chain 97.
   Registering with it succeeded immediately.

The signature was never the problem — both SDKs use `registerJob(uint256,address)`.
The `bag` CLI's docs describe it as `registerJob(jobId)`, which is the SDK
method rather than the contract ABI; the single-argument form does not exist
on-chain.

## Known limitation: delivery needs an out-of-band nudge

Both funded jobs sit at `FUNDED` rather than progressing to `SUBMITTED`.

This is expected and is the seller's integration surface, not ours. Per the
reference: *"The single seller runtime has no standalone poller — after funding,
send a `notify_funded` A2A message to the seller."* We could not send it: the
provider address is not registered on 8004scan for chain 97, so its A2A
endpoint is not discoverable from the registry, and no deliverable URL was
recoverable from its earlier completed jobs within the log windows public BSC
RPCs allow.

So the buyer side of ERC-8183 is complete and proven; the delivery half depends
on reaching a specific seller runtime out-of-band. `settleErc8183Job` is
implemented and remains untested, since no job of ours has reached `SUBMITTED`.

## Reproducing

```bash
npx tsx --env-file=.env.local scripts/hire-stepwise.mts          # attribute a failure
npx tsx --env-file=.env.local scripts/register-correct-policy.mts # the fix, isolated
npx tsx scripts/recent-jobs.mts                                   # surrounding job states
```

## Worth reporting upstream

The stale chain-97 policy address in `@altananetwork/sdk` breaks ERC-8183
hiring for every testnet buyer using that SDK, and the failure surfaces as an
undecodable `0xc94463e3` with no reason string. A one-line address change fixes
it.
