# ERC-8183

**Status: partial — blocked on `registerJob`, which reverts on the current BSC testnet deployment.**

Last verified: 2026-09-01, `@altananetwork/sdk@0.8.0`, BSC testnet (chain 97).

## What we intended

Commission a real job against an ERC-8183 seller from Pokter, follow it to
delivery, and release escrow — §34, and the "hire" end of the product loop.

## What works

| Step | Result | Evidence |
| --- | --- | --- |
| Deployment discovery | Working | Kernel, router, policy and $U all hold bytecode on chains 56 and 97 |
| Seller discovery | Working | Identified `0xdA61DfA4…` with three COMPLETED jobs at 0.1 $U across our categories |
| Balance preflight | Working | Returns `402` with the shortfall before submitting, rather than an opaque revert |
| `createJob` | **Working on-chain** | Job #864, [`0x0020d983…`](https://testnet.bscscan.com/tx/0x0020d983408965a1cd6fc4d82644f73fbbed54e457cf8e5619f11c7288b0745f) |
| `setBudget` | **Working on-chain** | [`0x94364efe…`](https://testnet.bscscan.com/tx/0x94364efe12e728637a8a84d4c9ab3a4c12b198ae35d48129995b0f8113320f90) — budget 0.1 $U |

So three of the five buyer calls execute successfully on-chain. Job #864 exists,
is ours, has its budget set and its $U approved. It cannot be funded.

## The failure, isolated

`hireErc8183Agent` batches five calls atomically, so the whole batch reverted
with one selector and no reason string. To attribute it, we created a job and
ran the calls individually:

```
1. createJob    CONFIRMED  0x0020d983…
2. registerJob  FAILED     0xc94463e3   <- root cause
3. setBudget    CONFIRMED  0x94364efe…
4. approve $U   CONFIRMED  0xd58107fc…
5. fund         FAILED     0x32d53d69   <- consequence
```

`registerJob(jobId, policy)` on the EvaluatorRouter is the root cause. `fund`
fails downstream because an unregistered job cannot be funded.

### What we ruled out

- **Not a funding problem.** Wallet holds 30 $U and 1.13 tBNB; allowance to the
  kernel is exactly 0.1 $U; budget is set on-chain.
- **Not the jobId race** the SDK documents. Reproduced deterministically across
  separate blocks.
- **Not a relay nonce artifact.** The first sequential attempt did surface
  `InvalidNonce` from firing intents back-to-back; re-running with delays gives
  the same `0xc94463e3`.
- **Not a platform outage.** Job **#863 COMPLETED at 0.1 $U** immediately before
  ours, so the rail is working for other buyers right now.
- **Not a stale policy address.** `policy.router` and `policy.commerce` both
  point back at the addresses the SDK uses.

### The unexplained part

`router.jobPolicy(...)` returns the zero address for jobs **852, 853, 858 and
863 — all COMPLETED**. Either successful buyers are not calling `registerJob` at
all, or the router stores the binding somewhere other than the accessor we can
read. We could not confirm which: the kernel is unverified on the testnet
explorer under an API key we have, so the custom error `0xc94463e3` could not be
decoded, and it is absent from the 4byte directory.

## Fallback

Per §33, the working subset is kept rather than removed, and the limitation is
surfaced rather than hidden:

- The hire API translates both selectors into plain language instead of showing
  a bare hex revert.
- `/my-agents` renders job state read from the kernel, so a funded job would
  appear the moment funding succeeds.
- Escrow release (`settleErc8183Job`) is implemented and untested, since no job
  of ours has reached SUBMITTED.

**Pokter does not claim ERC-8183 hiring works.** The Altana session layer — which
is fully working, 9/9 on its checklist — is what the product's hire flow
actually uses today.

## Reproducing

## Open question for the sponsor

Given job #863 completed minutes earlier at the same budget and provider: what
does a working buyer pass to `registerJob`, and is `0xc94463e3` a permission
check, a policy allowlist, or a state guard? The SDK's `buildHireCalls` passes
`(jobId, addresses.policy)`, which this deployment rejects.
